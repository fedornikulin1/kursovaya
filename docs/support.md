# Поддержка и панель управления

Пользователь открывает **Помощь** в шапке (на телефоне — значок `?`) или внизу сайта.
На `/help/` доступны 10 частых вопросов, поиск и фильтрация по разделу.
«Задать вопрос» открывает форму. Для личного обращения необходим вход в аккаунт.

## Работа сотрудника

1. Откройте `http://127.0.0.1:8000/admin/` и войдите существующим администратором.
   Ранее созданный суперпользователь и его пароль сохранены. Обычный демо-аккаунт
   студента не получает доступ к управлению.
2. На главной видны счётчики площадки и очередь «Нужен ваш ответ».
3. Откройте **Помощь и поддержка → Обращения в поддержку**. Фильтры позволяют
   выбрать статус, тему или дату; поиск работает по теме и автору.
4. Откройте обращение, прочитайте историю и заполните **Ответ пользователю**.
   Нажмите **Сохранить**. Ответ появится на странице обращения у пользователя.
5. После ответа статус станет «Поддержка ответила». Новое сообщение пользователя
   снова переведёт обращение в очередь «Ожидает поддержки».
6. Можно закрыть обращение одновременно с ответом, отметив соответствующий флажок.
   Без ответа закрытие и повторное открытие доступны действиями в списке.
7. Пользователь видит новые ответы по счётчику возле «Помощь» и в «Мои обращения».
   Обращение можно дополнить, закрыть или открыть снова. Открытый диалог обновляется
   кнопкой «Обновить переписку»; автоматического опроса в поддержке пока нет.

Частые вопросы редактируются в **Помощь и поддержка → Частые вопросы**.
Можно менять ответ, порядок и публикацию. HTML в ответах не исполняется.

Администратор также управляет пользователями и их профилями, категориями,
объявлениями, отзывами. В объявлениях есть миниатюры и действия публикации/архивации;
действия записываются в журнал Django Admin. Личные сообщения продавцов/покупателей
не зарегистрированы в панели управления.

## Отдельный сотрудник поддержки

Команда создаёт/обновляет роль с минимальными правами и сама никого не повышает:

```powershell
.\.venv\Scripts\python.exe manage.py setup_support_role
```

Администратор создаёт учётную запись обычными средствами Django Admin, включает
**Статус персонала** и назначает группу **Поддержка**. Права суперпользователя
сотруднику поддержки не нужны. Роль позволяет читать/отвечать на обращения и
просматривать базу частых вопросов; управление аккаунтами и объявлениями ей не доступно.
Для редактора FAQ можно отдельно выдать права изменения частых вопросов.

Если на новой установке администратора ещё нет:

```powershell
.\.venv\Scripts\python.exe manage.py createsuperuser
```

Не используйте общие демонстрационные пароли для опубликованного сайта.

## Архитектура для ВКР

`support/` — отдельное Django-приложение с тремя моделями:

- `SupportTicket`: автор, тема, раздел, статус и даты. Пользователь → обращения: 1:N.
- `SupportMessage`: обращение, отправитель, признак ответа сотрудника, текст,
  дата и отметка прочтения пользователем. Обращение → сообщения: 1:N.
- `FAQ`: раздел, вопрос, ответ, порядок и флаг публикации.

Переходы статусов и проверки доступа находятся в `support/services.py` и используются
HTML, API и админкой. Создание обращения атомарно: пустое сообщение не оставит
пустое обращение. Для одного пользователя действует лимит 5 новых обращений в час.
Ответы и смена статуса блокируют строку обращения на время транзакции. POST-формы
защищены CSRF, сервер проверяет длину текста. Пользователь может обращаться только
к своим заявкам; сотрудник отвечает через админку с отдельным разрешением.
HTML-страницы личных обращений не кешируются. Старые сообщения доступны только для
чтения и не редактируются через административную форму.

Панель расширяет стандартный Django Admin через `config/admin_site.py`; не требует
внешней темы или зависимости от отдельного сервиса. Сохраняются штатные вход,
проверки прав, журнал действий, поиск, фильтры и переключение светлой/тёмной темы.

## API для будущего приложения

Авторизация — та же сессия/CSRF или JWT, что и в основном API. Доступны:

- `GET/POST /api/v1/support/tickets/` — свои обращения / создать (`subject`, `topic`, `text`).
- `GET /api/v1/support/tickets/{id}/` — сведения и число непрочитанных ответов.
- `GET/POST /api/v1/support/tickets/{id}/messages/` — история (постранично, новые сначала) / дополнить (`text`).
- `POST /api/v1/support/tickets/{id}/read/` — отметить ответы прочитанными.
- `POST /api/v1/support/tickets/{id}/close/` и `reopen/` — закрыть/открыть.

Клиентское API не позволяет представляться сотрудником или менять автора.
Схема доступна на `/api/docs/` и в `docs/openapi.yaml`.

## ИИ на следующем этапе

Сейчас ответы дают сотрудник и редактируемая база FAQ; платный ИИ-сервис не подключён.
Для ВКР этот вариант работает без внешних ключей и позволяет показать полный цикл
обработки вопроса. Следующим этапом можно добавить генерацию **черновика ответа**
для сотрудника по опубликованным FAQ. Сотрудник проверяет и отправляет черновик сам.
Нужны серверный ключ, выбор провайдера, лимит расходов и правила передачи данных.
Пароли, личные переписки и содержимое чужих обращений не должны попадать в контекст.
